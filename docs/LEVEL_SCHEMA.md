# 关卡数据规范（LEVEL_SCHEMA）

> 这是给关卡设计者 / 后续维护者的唯一规范。**所有数值与表达式都不写死在代码里**，
> 关卡数据即调参面板：改一个数字就能调难度。

## 0. 设计流程（与策划案第 9 节一致）

1. 用 **二维数组 A** 画房间：只表示「墙 `#` / 地板 `.` / 虚空（空格）」，先不放元素。
2. 用 **二维数组 B** 给 A 里的格子写元素注释；`legend` 说明每个字符是什么元素。
3. 按**答案**设计：把一或几个房间当成一个独立区域，先想好这个区域的最优解（吃哪些元素、按什么顺序），
   填满所有房间后一路算到终点，**把最优解到达终点时的数值作为终点门门槛标准值 `goal.req`**。
4. 跑 `js/verify.js`（游戏内按 `V`）或 `node tools/verify-levels.mjs` 校验：
   可通关 / 门分隔两房间 / 门不相邻 / 房间密度 10%~30% / 表达式合法 / 门运算一定减少。

> 实际写关卡时，A 和 B 由 `js/map.js` 的构建器根据 `rooms + links + elements + fill` 生成，
> 生成结果可以直接在游戏内「导出 A/B」里看到（也是二维字符数组），方便逐格核对。

## 1. 关卡 spec 顶层字段

```js
{
  id: 1,                       // 关卡号 1..12（唯一）
  name: '白饭初尝',            // 关卡名
  subtitle: '第一关',          // 副标题（可省）
  tier: '入门',                // 难度标签（入门 / 初级 / 中级 / 高级 / 地狱）
  size: [34, 34],              // 地图宽高，必须满足档位下限（见 §6）
  sizeClass: '>30x30',
  seed: 1001,                  // 填充白饭的随机种子（可复现）
  intro: ['rice'],             // 本关要"介绍"的新元素类型（开局弹介绍卡）
  tips: ['把地板上的白饭全吃掉再去撞门'],   // 开局提示（可省）
  hint: '',                    // 常驻底部提示条文字（可省）

  // 铁盆可免疫失败，所以可用它设计"故意撞门"的关卡
  fill: { type: 'rice', value: 1, density: 0.16, clearance: 1 },

  rooms: [ ... ],              // 房间（见 §2）
  links: [ ... ],              // 走廊 + 门（见 §3）
  elements: [ ... ],           // 房间内元素（见 §4）
  start: { room: 'r0', at: [2, 2] },

  solution: ['rice_big', 'door_r0_r1', 'claude1', 'goal']   // 最优解顺序（见 §5）
}
```

### fill —— 大白饭填充（负责把房间元素密度顶到 10%~30%）

| 字段 | 说明 |
|---|---|
| `type` | 默认 `'rice'`；`'none'` 表示不填充 |
| `value` | 每颗填充白饭的数值（建议 1，最多 3） |
| `density` | 占房间地板格的比例，**必须让最终密度落在 (0.10, 0.30)**，建议 0.13~0.20 |
| `clearance` | 特殊元素周围留白的格数，防谜题被饭糊住（建议 1） |

单个房间可用 `rooms[i].fill = { density: 0.12 }` 覆盖；`fill:{type:'none'}` 可让某个房间不铺饭。

## 2. rooms

```js
{ id: 'r0', name: '前厅', at: [2, 2], wh: [12, 10], shape: 'rect', k: 2,
  cuts: [{ at: [0, 0], wh: [4, 4] }],   // 可选：在基础形状上再挖掉矩形（房间可以不是矩形）
  color: '#2a3f66' }                    // 可选：房间配色
```

* `at` 是房间左上角在**地图绝对坐标**中的位置，`wh` 是宽高。
* `shape`：`rect` | `round`（切四角，可用 `k` 指定切角大小）| `diamond` | `plus` | `cross` | `blob`（有机形状，用 `seed` 复现）。
* 房间之间**至少留 3 格间隔**，否则走廊与墙体生成会打架。
* 门必须能隔开两个房间 ⇒ 房间不要相互接触，连接一律走 `links`。

## 3. links（走廊 + 门）

```js
{ a: 'r0', b: 'r1',
  door: { id: 'door_r0_r1', type: 'door', op: 'sub', amount: 7, req: 20 } }
```

* 构建器自动在 a、b 之间找最近的边缘格，挖一条 1 格宽的 L 形走廊，并把门放在**走廊中段**（房间之外），
  从而保证「门隔开两个房间」「门可从任意方向进入」。
* 走廊不会穿过其他房间（构建器会挑不穿房间的走法）。
* 门与门之间自动保持距离 ≥ 3；若放不下会报错，此时调房间位置或换连接顺序。
* 一个房间可以有多条 links（即一个房间可以有两个门）。
* 门类型 `op`：
  * `'sub'` 减法门：`amount`（>0），通过后 `x = x - amount`
  * `'div'` 除法门：`divisor`（≥2），通过后 `x = ⌊x / divisor⌋`
  * `'expr'` 复杂运算门：`expr`（必须引用 `x`，且对任意 x ≥ req 都有结果 < x）
* 终点门写在 `elements` 里，类型 `goal`，不是 link。
* **中转站门不能是终点。** 终点只能是 `goal` 或 `hidden`。

## 4. elements

```js
{ id: 'rice_big', room: 'r0', at: [3, 4], type: 'rice', value: 12 }
```

* `room` + `at`（房间内局部坐标，从 0 开始）→ 自动换算成绝对坐标；也可直接用 `x` / `y` 绝对坐标。
* 必须在房间地板上，且同一格只能有一个元素。

| type | 额外字段 | 效果 |
|---|---|---|
| `rice` | `value` (>0) | 吃掉：`x += value` |
| `bowl_rice` | `value` (>0) | 吃掉：`x += value`，并获得铁盆（最多 1 个） |
| `token` | `expr`（含 `x`） | 吃掉：`x = expr(x)`（任意复杂运算，可直接改写数值） |
| `claude` | `factor` (>0) | 吃掉：`x *= factor` |
| `user` | `cond`（含 `x`）, `bonus`, `penalty`(可选，默认=bonus) | 条件为真（结果 > 0）：`x += bonus`；为假：`x -= penalty` |
| `goal` | `req`, 可选 `op/amount/divisor/expr` | `x ≥ req` 且 `x > 0` → 通关；否则失败。通用 `op` 先结算再通关 |
| `hidden` | `req`, `reveal` | `x ≥ reveal` 才显形；踏入时 `x ≥ req` → 通关，否则失败 |

### 表达式可用语法

`+ - * / % **`、比较 `== != < <= > >=`、逻辑 `&& || !`、变量 `x`、常量 `pi e true false`；
函数：`min max abs floor ceil round sqrt sign pow clamp div mod gcd lcm digitSum digitCount reverseNum sumDigits if`
（`/` 是**向下取整的整数除法**，`%` 结果非负；所有结果四舍五入到 3 位小数）。

## 5. solution（最优解顺序）

```js
solution: ['rice_a1', 'rice_a2', 'door_r0_r1', 'claude1', 'token1', 'user1', 'goal']
```

* 列出**最优解要按顺序吃掉/通过的所有非填充元素**（含沿途要过的门，最后一个是终点）。
* 校验器会按这个顺序，用 A\* 在「把其它未消耗的非填充元素当作障碍」的地图上找最短路径，
  再把这些路径拼起来用真实规则引擎逐步模拟，得到：
  * 每一步后的数值
  * 到达终点时的数值 = **该关最优值** `intendedValue`
  * 是否真的通关
* 校验器会检查 `goal.req <= intendedValue`，并提示「门槛标准值应设为 intendedValue」。
* 若 A\* 找不到路（说明该元素必须穿过另一个非填充元素才能吃到）会报错 —— 调整摆放位置即可。
* 填充白饭**不算障碍**（吃就完了），所以沿途会顺带吃掉若干白饭，数值会自然上涨，校验器已把这段算进去。

## 6. 档位与规模要求

| 关卡 | 规模下限 | 说明 |
|---|---|---|
| 1~5 | > 30×30 | 解释游戏元素机制，简单 |
| 6~8 | > 40×40 | 展示不同元素组合效果，初级 |
| 9~10 | > 50×50 | 更大的地图、更多元素，中级 |
| 11 | > 75×75 | 高级 |
| 12 | > 120×120 | 地狱：超大 + 超多元素 + 刁钻解法 + 复杂表达式元素 |

* 每关开局必须介绍**本关新增元素**（`intro` 数组）。
* 每关必须可通关（校验器强制）。
* 元素密度：每个房间 `(0.10, 0.30)` 开区间（校验器强制）。
* 表达式难度逐关递增：L1-4 只用算术；L5 起出现比较；L8 起出现 `&&`/`||`/函数；L11-12 用 `digitSum`/`gcd`/`mod` 等。

## 7. 实战经验（这些坑都真踩过，改关卡前务必看一遍）

### 7.1 `req: 'auto'` 的真实语义

| 写法 | 含义 |
|---|---|
| `req: 'auto'`（门） | 门槛 = 最优解**到达该门时**的数值 × `reqFrac`（默认 **0.8**） |
| `req: 'auto'`（终点门 / 隐藏格） | 门槛 = 到达时的数值 × `reqFrac`（默认 **1.0**，即策划案要求的"最优值即标准值"） |
| `reveal: 'auto'`（隐藏格） | 显形值 = 到达时的数值 × `revealFrac`（默认 **0.5**） |

反推是**两遍法**：先把所有 `'auto'` 临时置 0 跑一遍拿到每步真实数值 → 按上面的公式写入门槛 → **再跑一遍复核**，
确认带着真门槛仍然通关。所以只要 `solution` 写对了，关卡就不可能不可通关。

> 如果复核失败（例如某扇写死门槛太高），构建器会给一个保守门槛（1）保证还能玩，
> 同时在校验报告里**大声报错**："最优解路线在 lost 结束"。游戏内按 `V` 就能看到。

### 7.2 混沌函数 + 填充白饭 = 定时炸弹

`reverseNum` / `mod` / `gcd` / `digitSum` 的输出对输入极其敏感。填充白饭会让"到达某个元素的数值"
在 **±10** 范围内漂移，于是：

* `reverseNum(x) * 2 + 6`：到达 154 → 1146；漂到 161（回文数）→ 328。**差 3.5 倍**，后面整条链崩掉。
* 修法：**先钉住输入再进混沌函数**，例如 `reverseNum(x - mod(x, 10) + 5) * 2 + 6`（末位钉成 5，
  输出稳定在 1000~1200）。或者把混沌运算放在**只减不增的门**上，它就不会影响下游门槛。

### 7.3 `gcd` / `mod` 门的"正好归零"陷阱

`x - gcd(x, 36)` 在 `x = 36` 时结果是 **0** → 玩家刚好达标进入，出门就死。
凡是写死门槛的门，建议兜一个下限：`max(x - gcd(x, 36), 8)`。
校验器会给出「过门即死」告警，看到就要处理。

### 7.4 非矩形房间会吃掉坐标

`plus` / `diamond` / `cross` / `round` / `blob` 只保留部分格子。元素按房间局部坐标算出来很可能落在被挖掉的位置——
构建器会**自动就近落位**并在报告里告警，但请主动把关键元素（token / Claude娘 / 用户 / 铁盆饭 / 终点 / 隐藏格）
放在**房间中心 ±3 格**以内；要摆多个就沿中心横竖排开，彼此至少隔 1 格。

### 7.5 `solution` 的写法要点

* 未消耗的**非填充元素在寻路时被当作障碍**。所以路线顺序要保证"能绕开不想吃的东西"。
* 未消耗的**门也是障碍**：门必须在 solution 里按顺序出现，否则下一段找不到路。
* 填充白饭不算障碍，沿途会顺带吃掉，数值自然上涨，校验器已把这段算进去。
* **故意撞门（让铁盆碎）不需要写进 solution**：撞门不消耗元素、不改变数值，写进去反而可能挡住后面的路。
  校验器验证的是"不吃盆也能通关"，比"必须碎盆"更强的下界。
* 元素之间**至少隔 1 格**，否则 A\* 可能被迫穿过它，校验器会给"被迫穿过"的告警。

### 7.6 自测流程

```bash
node tools/verify-levels.mjs          # 改完关卡必跑；任何一关不过 exit 1
node tools/verify-levels.mjs --dump 7 # 导出二维数组 A/B + 最优解数值链，逐格核对
```

游戏内按 `V` 是同一套校验；`tools/verify.html` 是浏览器版，还能导出 A/B 原文。
仓库里的 GitHub Action 会在每次 push 时自动跑一遍，坏关卡进不了主干。
