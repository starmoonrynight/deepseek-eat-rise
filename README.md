# 蓝色大肥鱼吃大白饭

> 一个**纯前端、零依赖、零构建**的数值解谜网页游戏。
> 你是一只蓝色大肥鱼（DeepSeek 娘化），初始数值 **1**。
> 吃大白饭加数值、撞 token 改写数值、和 Claude 娘倍乘、被用户评判、
> 最后穿过一扇扇**中转站门**，用够格的数值走出中转站。

打开 `index.html` 就能玩（双击也行，不需要起服务器）。
也可以直接发布到 **GitHub Pages**。

---

## 快速开始

```bash
# 方式一：什么都不装 —— 双击 index.html 就能玩
# 方式二：起个本地服务器（推荐，手机同局域网也能玩）
python -m http.server 8080      # 然后浏览器打开 http://localhost:8080
# 方式三：用自带的零依赖服务器（会打印手机可访问的局域网地址）
npm run serve
```

### 想变成「点一个链接就能玩」

```bash
npm run build      # 打包成单文件 dist/index.html（样式/脚本/立绘全部内嵌，双击即玩）
```

发布到公网的四种方式（**最快的是把 `dist/` 拖到 Netlify Drop，一分钟拿到链接**）
见 **[docs/DEPLOY.md](docs/DEPLOY.md)**，里面有 GitHub Pages 的逐步操作（不需要装 Git，网页上传即可）。

游戏是纯静态的（传统 `<script>`，不是 ES module），`.nojekyll` 已经放好了。

## 操作

| 平台 | 移动 | 其他 |
|---|---|---|
| Windows | **按住** `方向键` / `WASD` → 连续平滑移动（松开后滑到格心停住）；**点相邻格子** → 精确走一格 | `+` / `−` 缩放　`R` 重开　`Z` 放大跟随/全图　`C` 图鉴　`I` 换形象素材　`L` 关卡　`M` 静音　`V` 关卡校验 |
| 安卓 / iOS | **按住**右下角虚拟方向键 → 连续移动；**滑动** → 走一格；**点相邻格子** → 走一格 | 点界面按钮 |
| 鼠标 | 点相邻格子走一格，或按住方向键 | 同上 |

### 移动与视角

* **连续平滑移动**：大肥鱼以恒定速度在格子上滑行（约 6.4 格/秒），不是一格一格地跳。
  想转弯时如果那一侧是墙，它会先直行，到下一个能转的格口再转过去。
* **放大跟随**：默认每格约 **64px**（一屏约 16×9.5 格），地图比窗口大，镜头随大肥鱼滚动。
  按 `+` / `−` 可以自己调缩放（0.6×~1.8×，会记住你的偏好）；按 `Z`（或点右上角 ⤢）在
  「放大跟随」和「全图总览」之间切换。
* **小地图**：跟随模式下左下角有小地图，标出你的位置、未通过的门（绿=数值够 / 红=不够）、终点和当前视野框。
* 屏幕边缘还有指向终点门的箭头，大图也不会迷路。

### 动画

大肥鱼是**图片立绘**，但所有动作都是实时变换算出来的（不占额外状态、与帧率无关）：

| 动作 | 表现 |
|---|---|
| 待机 | 上下浮动 + 呼吸起伏（轻微缩放） |
| 走路 | **走一格 = 一个小跳**：腾空 → 顶点拉长 → 落地压扁，同时裙摆左右摇；每踩到一个新格子脚下扬一小撮尘 |
| 转向 | 往右走时水平镜像，**让鲸鱼尾始终拖在身后**；头顶铁盆时会因头重脚轻晃得更明显 |
| 出生 | 关卡开始时从小弹到大 + 淡入，配一圈冲击环 |
| 通关 | 跳起来转一圈，落地压一下 |
| 失败 | 受击抖动 + 向侧面翻倒下沉，配合红色受击描边与判定范围弹窗 |

这套动画对**图片立绘和程序化画法同样生效**（两者共用 `charAnim()` 的一套参数），
所以换成你自己的立绘后动作照样在全。

URL 参数：`index.html#7` 直接进第 7 关；`index.html?all=1` 解锁全部关卡。

## 规则

* 大肥鱼碰到元素，就**用自己的数值参与该元素的运算**。
* **失败**：数值 ≤ 0，或者撞上一扇数值不达标的门。
* **成功**：走进终点门（或隐藏通关格）且数值 > 0。

### 元素一览

| 元素 | 效果 |
|---|---|
| 🍚 大白饭 | `x = x + 数值`（直接吃掉）。**每颗白饭身上都直接标着它自己的数值**，数值是关卡数据里逐颗设定的，不是随机的 |
| 🥣 铁盆大白饭 | 同大白饭，额外获得**铁盆**，形象变化为头顶铁盆 |
| 🪙 token | `x = 表达式(x)` —— 任意复杂运算，直接改写数值 |
| 🟠 Claude娘 | `x = x × 倍率` |
| 🟢 用户 | 判断运算：`cond(x)` 为真 → `x + 奖励`；为假 → `x - 惩罚` |
| 🚪 中转站门 | 三级：**减法门** / **除法门** / **复杂运算门**。数值 `≥ 门槛` 才能通过，通过后门消失变平地，且运算后数值一定减少 |
| 🏁 终点门 | `x ≥ 门槛` 且 `x > 0` → 通关 |
| 🟣 隐藏通关格 | 平时伪装成地板，数值达到**显形值**后浮现，踏入按终点门判定 |

**铁盆**：可免疫一次失败。触发时——元素**不消失**、数值**不变**、大肥鱼被**弹出碰撞范围**并有受击动画，铁盆碎裂。最多同时持有 1 个。

### 表达式

`+ - * / % **`、比较 `== != < <= > >=`、逻辑 `&& || !`、变量 `x`、常量 `pi e`。
函数：`min max abs floor ceil round sqrt sign pow clamp div mod gcd lcm digitSum digitCount reverseNum sumDigits if`。

> **除法是向下取整的整数除法**（`7 / 2 = 3`），取模结果永远非负，所有结果四舍五入到 3 位小数，
> 绝对值上限 1e12。这一套语义在 `js/expr.js` 里实现，游戏内「图鉴」也写明了。

## 已知问题与下一步（交接说明）

### 1. 求解器与真实复盘的可达性模型不一致（**优先修这个**）

**现象**：`tools/solve.mjs` 能搜出顺序，但 `verify.trace` 复算时走不通（返回 `playing`），
第 11 关就是卡在这里。

**根因**：两套模型对"数值"的演化不一致 ——

| | 求解器 | verify.trace（真实复盘） |
|---|---|---|
| 沿途的填充白饭 | **忽略** | 走过去就吃掉，数值随之上涨 |
| 被元素挡住时 | 直接换一条候选 | 有"被迫穿过"兜底：穿过去并把那个元素也吃掉 |

于是求解器眼里的数值和真实复盘出来的数值会分叉：用户条件是 `x % 4 == 3` 这类**精确余数**判断时，
真实数值偏一点就从"奖励"翻成"惩罚"，后面的门可能因此过不去。

**修法（二选一）**：
* **A（推荐）** 让求解器也模拟填充白饭：状态里带上"走到目标格沿途吃到的白饭"，
  等于把 `trace` 的寻路结果喂回求解器；
* **B** 把 `trace` 的"被迫穿过"去掉，改成**硬失败**，让两边都严格拒绝不干净的路线
  （实现简单，但会让小房间关卡更难解）。

两边统一之后，第 11 关就能从 `js/levels.js` 的 `DISABLED` 名单里放出来。

### 2. 生成器的 `size` 没算上抖动

`buildAct4()` 返回的 `size` 用的是基准宽高，但房间有 ±2 的坐标抖动和 ±2 的宽高浮动，
所以最后一列/最后一行房间可能超出地图边界（第 36 关实测超出 2 格）。

**修法**：改成按生成后的真实房间范围算 ——

```js
var maxX = 0, maxY = 0;
rooms.forEach(function (r) { maxX = Math.max(maxX, r.at[0] + r.wh[0]); maxY = Math.max(maxY, r.at[1] + r.wh[1]); });
// size: [maxX + 3, maxY + 3]
```

⚠️ 注意：改 `size` 会重排整张图，第 19~36 关的解都要重新跑 `npm run apply`。

### 3. 枢纽走廊的"交汇处预留宽度"

已经实现的规则（`js/map.js` 的 `pathMergesOther`）：新走廊的每一格，
除自己前后两格以外四邻必须还是墙 —— 否则两条走廊会并成大厅，
门旁边凭空多出通路，**可以绕过门**（策划实测到的问题）。

但枢纽房间挂 6~8 条走廊时满足不了这条规则，所以：

* 多段 Z 形拐弯走廊（`pathBetweenZ`）**当前关闭**
* 枢纽连线（`hubs`）**当前关闭**（第五幕的 `hubs: []`）

**要打开必须先做**：让枢纽的每条走廊从**不同方向的边缘**接入，并保证走廊之间留 1 格墙。

### 4. 立绘更新

`assets/fish_bowl.png`（铁盆形态）已换成新图，代码里所有立绘 URL 都带了 `?v=3` 防缓存。
**GitHub Pages 上那份还是旧的，需要重新上传 `assets/` 文件夹**。
另外如果以前把图拖进游戏存过 localStorage，它优先级更高 —— 按 `I` 打开形象面板点「恢复程序化形象」清掉。

## 36 个关卡（五幕 · 当前上线 35 关）

| 幕 | 关 | 规模 | 场地 | 算法 |
|---|---|---|---|---|
| 第一幕 基础 | 1-12 | 房间 5×5~10×10 | 浅海 | 只用第 1 关解锁的 20 个基础函数 |
| 第二幕 算法 | 13-24 | 同上 | 深海 | 第 13 关起解锁 `chunk/snap/digitAt/headDigit`，第 19 关起解锁 `sumRange/tri/median/avg` |
| 第三幕 高阶 | 25-36 | 自由布局（房间抖动、宽高浮动） | 海沟 / 热泉 / 深渊 | 第 25 关起解锁 `fold/collatz/popcount/bitLen/isPrime/nthPrime/xor/band/bor` |

**算法解锁是强制的**：`js/levels.js` 的 `FUNC_SCHEDULE` 规定每个函数最早能在第几关出现，
`js/verify.js` 会逐条扫描元素表达式，发现"用了还没介绍的算法"直接报错。
每关新解锁的算法会自动生成开场介绍面板。

> 第 11 关当前**下架**（`js/levels.js` 的 `DISABLED`），原因见上面的交接说明第 1 条。

| 幕 | 关 | 规模 | 新机制 |
|---|---|---|---|
| 第一幕 | 1-6 | 34×34 ~ 44×44 | 白饭 / 铁盆 / Claude 倍乘 / token 改写 / 用户 / 隐藏格 |
| 第二幕 | 7-12 | 46×46 ~ 124×124 | 多门链、clamp 门、数位门、地狱级 126 房间图 |
| 第三幕 | 13-18 | 58×52 ~ 95×76 | 余数门、复合逻辑条件（`&&` `||` `!`）、四通枢纽、**双门走廊**（一条路上两道门，中间夹 4×4 中转屋）、`min`/`max`/`if`/嵌套函数门 |
| 第四幕 | 19-24 | 128×94 ~ 166×118 | **20~30 房间**的大图（参数化生成）、条件池、门型池按数值规模缩放 |

难度增长按策划要求逐条落实：房间里的复杂元素更多（每间 1~4 个）、
一个房间同时联通多个房间（网格生成树 → 内部房间最多连 4 个邻居）、
一条路径上多道门（中转屋串成的双门走廊）、用户条件越来越复合、
门的运算从减法/除法一路到 `min(x − a, max(floor(x / 2), b))` 这种嵌套式。

### 房间尺寸与"补元素"工序

策划要求**单房间 ≤ 35×35**。实测 24 关里最大的房间是第 12 关的 **24×24**，
其余都在 11~22 之间，所以尺寸本身一直是达标的，不需要重画地图。

真正调整的是**房间里特殊元素的数量**。做法是在 `js/levels.js` 的构建期加一道工序
`enrichLevel()`：房间建好之后按面积补元素（约每 45 格 1 个，3~8 个封顶）。三条安全规则：

1. **只补这一关已经出现过的元素类型** —— 第 1 关没有 Claude 娘就绝不会冒出 Claude 娘，教程顺序不破；
2. **新元素四邻必须都是空地、并留 1 格净空** —— 否则会堵死走廊口，把关卡变成不可解；
3. 不碰放着终点/隐藏格的那一格。

实测效果（第 24 关）：`user 6→26`、`token 5→25`、`claude 9→29`、`bowl 6→25`。
工具链（`solve` / `prune`）也走同一个 `levels.buildSpec()`，所以求解和校验看到的图和游戏完全一致。

### 这一版新加的复杂运算

`js/expr.js` 里新增 17 个函数，让关卡设计不必反复写 `x + 常数`：

| 函数 | 含义 | 例子 |
|---|---|---|
| `chunk(x, n)` | 抹零到 n 的整数倍 | `chunk(1234, 100) = 1200` |
| `snap(x, n)` | 就近吸附到 n 的倍数 | `snap(107, 25) = 100` |
| `fold(x, n)` | 在 [0, n] 之间来回折返 | `fold(31, 10) = 9` |
| `collatz(x)` | 偶减半 / 奇 3x+1 | `collatz(7) = 22` |
| `xor` `band` `bor` | 位运算 | `xor(12, 10) = 6` |
| `popcount(x)` `bitLen(x)` | 二进制里 1 的个数 / 位数 | `popcount(23) = 4` |
| `digitAt(x, i)` `headDigit(x)` | 第 i 位数字 / 最高位 | `digitAt(90210, 2) = 2` |
| `sumRange(a, b)` `tri(n)` `fib(n)` | 等差求和 / 三角数 / 斐波那契 | `fib(12) = 144` |
| `isPrime(n)` `nthPrime(k)` | 质数判定 / 第 k 个质数 | `nthPrime(10) = 29` |
| `median(a,b,c)` `avg(...)` | 三数取中 / 变参平均 | `median(9,3,5) = 5` |
| `ceilDiv(a, b)` | 向上取整除法 | `ceilDiv(17, 5) = 4` |

其中 `chunk` / `snap` / `fold` 特别适合做门 —— 它们天然满足"过完一定减少"这条硬规则。
补元素工序生成的 token 和用户条件已经在用这批函数（例如
`chunk(x, 100) + tri(digitCount(x)) * 7`、`popcount(x) > 5 || x > N`）。

> 注意：表达式引擎**没有**三目运算符 `? :`，条件取值请写 `if(cond, a, b)`。

校验器逐关检查这些东西，任何一条不过就让脚本 exit 1（CI 也会红）：

* 地图尺寸达到档位下限（`>30×30` / `>40×40` / `>50×50` / `>75×75` / `>120×120`）
* 每个房间的元素密度**严格落在 (10%, 30%)**（实测全部在 12.8% ~ 16.7%）
* 每扇门都真的**隔开两个房间**（把门当墙做连通性检查）
* 门与门**不相邻**，且每扇门都至少能和另一扇门在同一条可通行路径上
* 门的运算**一定减少**（在采样区间上逐点验证 `f(x) < x`）
* 所有 token / 用户 / 门的表达式能解析、引用了 `x`
* **最优解路线真的能通关**（BFS 找路 + 真实规则引擎逐步模拟）
* 终点门槛 **≤ 该关最优值**（`req:'auto'` 时就是最优值本身）

## 关卡是怎么保证"一定能通关"的

这是这个项目最核心的设计，完全对应策划案第 9 节：

1. **两层地图**：`js/map.js` 的构建器先生成**二维数组 A**（只描述墙 / 地板 / 虚空），
   再生成**二维数组 B**（逐格写元素注释，配 `legend` 说明每个字符是什么元素）。
   游戏内按 `V` 或打开 `tools/verify.html` 可以把任意一关的 A / B 原文导出来。
2. **按答案设计**：每一关的 spec 都写了 `solution`——最优解要按顺序吃掉的元素 id（含沿途要过的门，最后是终点）。
3. **门槛反推**：加载关卡时，`js/verify.js` 会按 `solution` 用 BFS 在
   「未消耗的非填充元素视为障碍」的地图上逐段寻路，把整条路径交给**真实规则引擎**逐步模拟，
   得到每一步的真实数值，然后把终点门槛写成到达终点时的数值（`req:'auto'`）。
   —— 这正是「**将最优值作为终点通关条件标准值**」。
4. **复核**：带着真实门槛再跑一次完整路线，确认真的能通关；不通过的话游戏内会直接提示（按 `V` 看详情）。

### 顺序不是拍脑袋写的：求解器

`tools/solve.mjs` 用 beam search 搜「最优吃元素顺序」：状态是 `(已吃集合, 当前数值)`，
可达性用**和游戏同一套**的逐格 BFS 判定（没开的门就是挡路的），结算用**同一套** `rules.apply`。

它会自然搜出这条策略：**先凑够门槛把门开了 → 去别的房间吃 → 回头再吃留下的高价值元素**。
道理很直白 —— 削减型门（减法 / 除法 / clamp / 余数）带过去的数值越多亏得越多，
而倍乘应该留给后面的大额白饭。改用它之后最优值抬了一大截：

| 关 | 旧（一个房间吃完再走） | 新（先开门、回头再吃） |
|---|---|---|
| 3 | 200 | **266** |
| 4 | 284 | **897** |
| 5 | 117 | **434** |
| 6 | 82 | **382** |
| 7 | 86 | **403** |
| 12 | 2978 | **23927** |

```bash
npm run solve     # 求解：最优顺序 + 每扇门的极限值（会打印"没用到"的元素）
npm run apply     # 把求解结果写回 js/levels/*（同时把写死的门槛改成 auto）
npm run prune     # 找多余元素：逐个试删 + 真实引擎复算，只有数值一模一样才真删
```

`prune` 的结论值得一提：**一个都删不掉**。每个"最优解没用到"的元素，
删掉后要么让数值变了一两点（它是挡路的障碍，影响沿途吃到的白饭），
要么直接让关卡不可解（它是备用路线）。所以关卡里没有真正的冗余元素。

   写 `'auto'` 时的松紧旋钮：`reqFrac`（门默认 **0.8**、终点默认 **1.0**）、`revealFrac`（隐藏格显形值默认 **0.5**）。
   把 `goal.req` 写成 `'auto'` 就等于「**最优值即通关标准值**」——实测 12 关里有 5 关是这样对齐的，
   另外 12 关的门槛现在**全部**是反推出来的（`req:'auto'`，`reqFrac` 默认 1），
   也就是「最优解走到这扇门时的真实数值」＝ 这扇门的**极限数值**，没有手工凑的数字了。

5. **硬性校验**（游戏内 `V` / 命令行 / `tools/verify.html` 三处同一套）：
   * 地图尺寸达到档位下限
   * 每个房间元素密度严格落在 **(10%, 30%)**
   * 每扇门都真的**隔开两个房间**（把门当墙做一次连通性检查）
   * 门与门之间**不相邻**，且每扇门都至少能和另一扇门在同一条可通行路径上
   * 门的运算**一定减少**（在采样区间上逐点验证 `f(x) < x`）
   * 所有 token / 用户 / 门的表达式都能解析、都引用了 `x`
   * 最优解路线真的能到达终点并通关

> **设计关卡时最容易踩的坑（都是实测踩过的）**
>
> * **混沌表达式 + 填充白饭 = 定时炸弹**。`reverseNum` / `mod` / `gcd` 这类函数，输入被沿途白饭推动 ±10
>   就可能让输出差 10 倍。第 12 关原本写 `reverseNum(x)*2+6`：到达值 154 时给 1146，
>   被白饭漂到 161 时因为 161 是回文数只给 328，后面整条链崩掉、9 号门直接把玩家打成 −20。
>   现在的写法是 `reverseNum(x - mod(x, 10) + 5) * 2 + 6`（先钉住末位再反转，输出稳定在 1000~1200）。
>   **要么给混沌函数钉住输入，要么把它放在只减不增的门上。**
> * **`gcd` 门会「正好减到 0」**：`x - gcd(x, 36)` 在 x=36 时结果就是 0，玩家刚好达标反而送命。
>   写死门槛的门建议兜一个下限，例如 `max(x - gcd(x, 36), 8)`。
> * **非矩形房间会吃掉坐标**：`plus/diamond/cross/round/blob` 只保留部分格子，元素按房间局部坐标算出来
>   可能落在被挖掉的空位上。构建器会自动就近落位并在校验报告里告警，但关键元素请放在房间中心 ±3 格内。

命令行校验：

```bash
node tools/verify-levels.mjs          # 校验 12 关，任何一关不过就 exit 1
node tools/verify-levels.mjs 12       # 只看第 12 关
node tools/verify-levels.mjs --dump 9 # 导出第 9 关的二维数组 A / B 与最优解数值链
node tools/smoke.mjs                  # 端到端冒烟：stub DOM 里真跑一遍游戏
```

`tools/smoke.mjs` 会在 Node 里用一套 stub DOM 把整个游戏跑起来，逐项断言：
第 1 关按最优解真按键通关且数值 == 该关最优值 / 撞门失败的判定范围弹窗 /
**数值 ≤ 0 的失败判定确实触发** / **铁盆免疫一次失败（盆碎、数值不变、元素留原地、人被弹回）** /
**立绘真的被画出来且尺寸、锚点正确** / **12 项动画断言（小跳、压扁拉长、摇摆、受击抖动、出生弹入、通关转圈、失败翻倒、铁盆晃动、水平镜像）** /
**不剧透（气泡只写规则不写算好的数、门不显示能否通过、没有撤销入口）** / assets 立绘是合法 PNG。
实测 **61 项全过**。两条命令都挂在 `npm test` 和 GitHub Action 上。

### 刻意"不剧透"

这是个要动脑算数值的解谜游戏，所以界面上**只给规则、不给答案**：

* 元素气泡写 `<b>x =</b> (x+4)*2`、`<b>x × 3</b>`、`若 x>=20 则 +15，否则 −15`，
  **不会**预告"算出来是多少"；
* 中转站门写明 `门槛 ≥N` 和 `通过后 x − 7`，但**不会**告诉你现在数值够不够
  （不再有绿/红变色、✅/⛔、"差 N"）；
* 没有撤销功能——走错了只能重开，逼你把每一步算清楚；
* 只有白饭的数值例外：它本来就逐颗印在饭上（那是输入，不是结果）。

失败弹窗里的"需要 x ≥ 38，当前 x = 1"是**事后**的判定范围说明，不是提前剧透。

想换成你自己的图，有三种方式（任选）：

1. **直接拖进去**：把图片拖到游戏画面上松手，弹出面板选「常态形象」或「铁盆形态」。
   图片存进浏览器本地存储，下次打开还在。也可以按 `I` 或点 📖 图鉴 →「换形象素材」。

3. **关掉图片**：把 `js/main.js` 里 `USE_IMAGE_ASSETS` 改成 `false`，回到纯程序化画法。

> 带场景背景的图（例如 3D 渲染）会自动抠背景：先把边缘同色区域洪水填充掉，
> 再沿渐变吞掉阴影，最后按行算出角色剪影、清掉两侧残留 —— 三步都不伤角色本体。
> 抠图前后可以用 `tools/prep-art.py` 离线处理，效果更可控：
>
> ```bash
> python tools/prep-art.py        # 处理 assets/fish.png 与 assets/fish_bowl.png
> ```
>
> 脚本会先把原图备份成 `*.png.bak.png`，之后反复运行都会从备份重来，不会二次抠图。
> 只给 `fish.png`、没给 `fish_bowl.png` 时，程序化画法会把不锈钢盆扣到你的立绘上，
> 「带铁盆后形象变化」这条玩法不会丢。

## 调难度

所有数值和表达式都在关卡数据里，改一个数字就能调难度，**不用动任何逻辑代码**：

* 白饭数值 → `elements` 里的 `value`（**逐颗单独设置**，例如 `{id:'rice_a', type:'rice', value:36}`；
  房间批量铺的白饭用 `fill.value`）；房间铺饭密度 → `fill.density`（记得保持在 10%~30%）
* 门的门槛 → `door.req`；写成 `'auto'` 就是「按最优解到达时的数值反推」，
  再用 `reqFrac`（默认门 0.8、终点 1.0）当松紧旋钮
* 终点门槛 → `goal.req`，写 `'auto'` 就是策划案要求的**最优值即标准值**
* 表达式 → `token.expr` / `user.cond` / 复杂运算门 `door.expr`

字段说明见 [`docs/LEVEL_SCHEMA.md`](docs/LEVEL_SCHEMA.md)。
